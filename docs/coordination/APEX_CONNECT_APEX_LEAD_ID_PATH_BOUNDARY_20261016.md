## Confirmed source-level defect and isolation repair

Originally `updateApexLeadStatus(leadId)` and the admin follow-up API interpolated the incoming `leadId` directly into `path.join(..., \`${leadId}.json\`)` and accessed the resulting local filesystem path without canonical ID validation. A malformed path-like ID therefore risked escaping the intended lead JSON directory in source-level path construction. Both HTTP routes were already SaaS-admin authenticated; **no actual unauthorized production file access or exploitation was attempted or claimed**.

The canonical lead-ID format comes directly from the application's existing generator: `LEAD-` plus exactly eight uppercase UUID hex characters. The fix enforces that exact format in a shared library guard, constructs all per-lead paths through an enforcing `leadFilePath` helper, and exposes `readApexLeadById` so follow-up no longer builds a separate unchecked path. Both admin route handlers explicitly return HTTP400/no-store on invalid ID **after** their existing `requireSaasAdminUser` check and **before** reading body or touching any file. Existing 401/403, valid status updates and follow-up email paths remain intact. The storage helper rejects direct callers with malformed IDs before any read/write.
