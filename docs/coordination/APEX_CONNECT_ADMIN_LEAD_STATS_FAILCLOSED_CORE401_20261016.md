## Product defect and narrow implementation

Original authenticated admin stats route returned `success:true` without explicit no-store on 200, and returned 401/403 without no-store. Admin page's `loadLeadStats()` only updated cached counts on a happy success path; on HTTP401/403/500, transport failure, malformed JSON or fast filter changes it preserved previous numbers with no error state. Older responses could overwrite newer totals. That could make an outage or revoked session look like a current success, and could allow stale privileged aggregates to remain in the browser. This is a **source-level integrity/privacy risk**, not an observed production breach.

**New exact four-file scope:** `src/lib/client/apex-lead-list-request.ts` adds strict `fetchValidatedLeadStats` (HTTP ok, successful JSON envelope, nonnegative safe-integer status/type totals with matching sums and supported types, explicit no-store); `src/app/api/saas-admin/apex-leads/stats/route.ts` adds `Cache-Control:no-store` to both 200 and 401/403, preserving the existing authenticated, redacted HTTP500 response; `src/app/saas-admin/apex-leads/page.tsx` adds monotonic request tickets, invalidates old stats on filter changes, clears old counts before retry, shows an accessible temporary error state and retry button, and never resurrects older failed-filter responses; new `tests/apex-admin-lead-stats-failclosed.test.cjs` tests genuine TypeScript-transpiled handler/helper and UI contract. Existing lead creation, atomic status replacement, lead file storage, authenticated admin listing and CSV safety remain untouched.
