## Reproduced defects / correction
1. The login API returns `success:true, mustChangePassword:true` without a portal token for a teacher whose account requires temporary-password rotation. Prior `LoginClient` incorrectly called `contextLogin` before redirecting to the challenge. That optimistic identity initialization can race session verification/clear and cause the browser to jump back to login. **Fixed in source:** challenge response goes only to exact same-origin `/auth/change-password?userId=<numeric>` and does not hydrate the portal context.
2. On a regular successful login, `LoginClient` previously navigated based on the optimistic response. **Fixed in source:** require an independent same-origin `/api/auth/me` response with matching user identity and role portal before storing user context and navigating.
3. Existing signed browser tokens must not survive an authorized password reset. **Fixed in source:** `getCurrentUser` rejects accounts flagged `must_change_password` before building the authenticated response; DB query remains read-only and restricted to canonical session actor.
4. **Separate confirmed LIVE release drift, NOT fixed by the patch alone:** live `https://api.assps.edu.pk/dashboard` 307 redirects to `/admin` unconditionally; Next `next.config.ts` in deployed gitless `/var/www/apex-connect` has extra `/dashboard` redirects absent from reviewed source. The intended canonical proxy sends anonymous user to `/login?next=/admin` and signed teachers to their own portal. The 5-route live check remains 4/5 FAIL. Must be corrected only as part of Core-controlled, verified, rollback-capable production promotion.
